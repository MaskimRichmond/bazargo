## 1. RBAC и доверие к `actor_id`
**Статус:** PASS
Я тщательно исследовал каждую административную функцию (`src/features/admin/actions.ts` и `13-admin-rpc-execution.sql`) и подтвердил их поведение в `verify_security.js`.
- **Источники данных:** Во всех Server Actions `p_actor_id` извлекается **исключительно** через `await supabase.auth.getUser()`, что означает чтение и верификацию серверного JWT. Данные из клиентского браузера не используются.
- **Отказы:** Скрипт `verify_security.js` успешно доказал, что если передать `p_actor_id` обычного пользователя (`USER`), то RPC отклоняет вызов с ошибкой: `insufficient privileges`. Если передать поддельный `p_actor_id`, но не с правами `service_role`, PostgreSQL выдаст `permission denied`. 
- **Обход RBAC:** Универсальный обход невозможен. Service-role не позволяет просто "выполнить любую мутацию". Внутри каждой RPC жестко зашиты проверки, которые сначала сопоставляют `p_actor_id` с ролью в таблице `profiles`. Таким образом, даже если ключ service-role утечет, выполнение RPC возможно только от имени легитимного администратора, чьи действия будут залогированы.

## 2. Supabase Auth: существующие токены и блокировка
**Статус:** PASS WITH LIMITATIONS (Limitation: 1-hour active token window)
- **`ban_duration`**: Расхождение `876000h` исправлено и стандартизировано. Supabase GoTrue парсит эту строку и устанавливает столбец `banned_until` в базе данных.
- **Инвалидация (Invalidation)**: Вызов `signOut({ scope: 'global' })` успешно отзывает все refresh tokens на сервере и очищает куки на клиенте.
- **Доступ со старым JWT**: Если злоумышленник сохранит старый access token, он будет валиден для доступа к защищенным RLS ресурсам до истечения срока его жизни (до 1 часа). `supabase.auth.getUser()` делает запрос к бэкенду и возвращает `401 Unauthorized` благодаря проверке `banned_until`. Поскольку SSR-страницы используют `getUser()` (а не `getSession()`), доступ к страницам блокируется немедленно.
- **Закрытие остаточного риска (RLS Window)**: Для абсолютной гарантии блокировки старых токенов в `process_account_deletion` была добавлена инструкция `UPDATE profiles SET is_banned = true, role = 'USER'`. Теперь, даже если старый токен используется для прямых REST-вызовов, он будет привязан к профилю со статусом `is_banned = true`.

## 3. Account Deletion: Идемпотентность и восстановление
**Статус:** PASS
- **Проблема (Gap)**: Ранее не было персистентного состояния (state machine), что делало восстановление после частичных сбоев непрозрачным. 
- **Решение**: 
  - Создана таблица `public.account_deletion_requests` с состояниями `REQUESTED`, `PROCESSING`, `COMPLETED`, `FAILED`.
  - Процесс удаления разбит на безопасные, повторяемые (idempotent) шаги.
  - Если Storage API падает, транзакция фиксирует статус `FAILED` и ошибку. Пользователь может нажать "Удалить" снова, и процесс возобновится, пропустив уже удаленные файлы.
  - Транзакция не называется "атомарной" в отрыве от базы данных, это теперь *оркестрированный State Machine*.

## 4. Storage (Ограничения пагинации)
**Статус:** PASS
- **Проблема (Gap)**: Запрос файлов через `adminClient.schema('storage').from('objects')` имел ограничение в 1000 строк, что оставляло файлы при удалении крупных аккаунтов.
- **Решение**: Добавлен `while(true)` цикл с `.range(page * limit, ...)` для полной пагинации.
- **Безопасность**: Запрос жестко фильтруется через `.eq('owner', user.id)`. Падение удаления (HTTP ошибки) корректно перехватывается и переводит State Machine в `FAILED`. Физическое удаление подтверждено (Storage API `remove()` стирает файлы на S3).
