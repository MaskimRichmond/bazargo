# BazarGo: Комплексный Архитектурный Аудит и Целевая Модель

## 1. Краткое описание продукта и текущего состояния
BazarGo — это кроссплатформенный маркетплейс (Web, Mobile Android/iOS) для рынка Кыргызстана. Платформа поддерживает C2C-продажи, магазины, B2B-закупки, биржу заявок на товары и внутренние чаты.
**Текущее состояние**: Проект находится в стадии готового MVP. Разработка переведена в формат монорепозитория (npm workspaces).
- **Web (Next.js)**: Реализованы все основные разделы, включая административную панель.
- **Mobile (React Native + Expo)**: Реализованы основные пользовательские маршруты (каталог, корзина, создание объявления, заказы продавца), но отсутствуют некоторые экраны (Настройки профиля, чаты, детальная карточка товара, магазины).
- **Backend (Supabase)**: БД (PostgreSQL) включает 43 миграции. Покрыты RLS, триггеры, RPC и сложные state-машины для статусов сущностей.

## 3. Текущая и Целевая архитектура

### Текущая архитектура
Вся система работает в едином монорепозитории (`bazargo-monorepo`):
- `apps/web/`: Клиентская часть (Next.js 14). Содержит UI, Server Actions (работают через `service_role` или `auth_token`), локализацию (`next-intl`) и админ-панель.
- `apps/mobile/`: Мобильное приложение (React Native / Expo). Обращается к Supabase напрямую через клиент.
- `packages/shared/`: Общие типы (TypeScript) и Zod-схемы валидации.
- `supabase/`: SQL миграции, RLS, RPC, Storage, pgTAP тесты.

### Целевая архитектура
Архитектура не нуждается в кардинальном пересмотре. Текущее модульное разделение Web, Mobile и Shared достаточно для поддержки.
Требуемые изменения:
1. **Единый слой API для тяжелых транзакций**: Расширение RPC в БД, чтобы Web и Mobile имели 100% одинаковую бизнес-логику (как уже сделано для `create_orders_from_cart`).
2. **Mobile Completeness**: Добавление недостающих экранов в мобильное приложение (Чаты, Карточка товара, Удаление аккаунта).
3. **Storage Abstraction**: Реализация надежной загрузки бинарных файлов на Mobile (FormData/Blob), так как текущий код `expo-image-picker` работает только с локальными `file://` URI.

## 5. Фактическая и Целевая ER-диаграммы (БД)

**Фактическая модель данных (Существующая):**
- **Auth & Profiles**: `auth.users` -> `profiles`. `profiles` содержит роль, телефон.
- **Catalog**: `categories` (древовидная), `products` (legacy-таблица), `listings` (основные товары), `listing_images` (связь 1:N).
- **Stores & B2B**: `stores` (статусы PENDING, ACTIVE), `b2b_applications`, `b2b_offers`.
- **Commerce**: `cart_items`, `orders`, `order_items`.
- **Engagement**: `favorites`, `follows`, `chats`, `messages`.
- **Bidding**: `requests`, `request_offers`.
- **Admin**: `reports` (полиморфная target_id/target_type), `audit_logs`, `account_deletion_requests`, `user_blocks`.

**Сравнение и Целевая модель:**
Модель данных хорошо продумана, но имеет небольшие проблемы целостности:
1. **Уведомления**: Таблица `notifications` ссылается на `user_id`, но часто использует строковый `link` вместо строгих foreign keys к сущностям.
2. **Полиморфизм**: `reports` и `audit_logs` используют полиморфные связи (target_id без FK), что мешает каскадному удалению и строгой целостности.
3. **Products**: Существует старая таблица `products`, в то время как весь фронтенд работает с `listings`. Ее нужно безопасно удалить, если она пуста.

## 6. Административная панель BazarGo
Реализована в `apps/web/src/app/[locale]/(main)/admin`.
- **Главная (Overview)**: Сводка по активным пользователям, объявлениям и заказам.
- **Управление пользователями (`/users`)**: Просмотр, выдача прав (ADMIN, MODERATOR), блокировка (бан) и апелляции.
- **Модерация объявлений (`/listings`)**: Фильтр по статусу (PENDING). Кнопки "Одобрить", "Отклонить" (с указанием причины).
- **Жалобы (`/reports`)**: Очередь жалоб, назначение решений, изменение статуса (OPEN -> IN_PROGRESS -> RESOLVED).
- **Магазины (`/stores`)**: Одобрение заявок на магазины.

*Роли и разрешения*: Реализованы через проверку роли в таблице `profiles`. Доступ к `/admin` закрыт Middleware и RLS.

## 7. Безопасность и Целостность (Security Audit)
- **RLS**: Политики полностью включены. Пользователи могут изменять только свои `listings`, `orders`, `profiles`.
- **Мягкое удаление**: Вместо DELETE объявления переводятся в статус `ARCHIVED`. Это защищает целостность истории заказов.
- **Атомарные RPC**: Подтверждение заказов (`confirm_order`, `complete_order`) использует `FOR UPDATE` блокировки, предотвращая race conditions при списании остатков.
- **Ограничения (Rate Limiting)**: Отсутствует на уровне базы данных для создания сообщений. Рекомендуется добавление таблицы `rate_limits` или использование Nginx/Vercel Middleware.

## 8. Производительность и масштабирование
- **Индексы**: Большинство индексов создано. Не хватает индексов на внешних ключах в таблицах `b2b_offers` (listing_id, buyer_id) и `reviews` (reviewer_id).
- **Кэширование**: Next.js использует `fetch-cache` для страниц каталога. Для Mobile необходимо кэширование на уровне клиента (TanStack Query / SWR), которое пока отсутствует.
- **Пагинация**: Требуется внедрение курсорной пагинации для каталога (сейчас используется LIMIT/OFFSET или загрузка больших списков).

## 9. План Тестирования
- **Unit (Schema/Validation)**: Проверка Zod-схем в `packages/shared`.
- **Database (pgTAP)**: Тесты RLS, RPC и триггеров в `supabase/tests/database`.
- **E2E (Playwright)**: Сценарии Web: регистрация, создание товара, покупка через B2B, админ-модерация. (Сейчас тесты E2E падают при отсутствии БД).
- **E2E Mobile**: Тестирование через Maestro/Detox (отсутствует).
