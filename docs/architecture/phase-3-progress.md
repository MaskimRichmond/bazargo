## 2. Безопасность и архитектурный аудит
Я провел функциональный и ручной SQL-анализ механизмов безопасности, который подтвердил, что:
- **Административные RPC (`admin_change_user_role`, `admin_moderate_listing` и др.):** Все действия защищены строгой проверкой роли `p_actor_id` внутри базы данных. Защита RLS не позволяет обычным пользователям читать закрытые разделы или подменять ID. Ни один ADMIN не может назначить кому-то `SUPER_ADMIN`.
- **Удаление аккаунта:** Осуществляется через State Machine (таблица `account_deletion_requests` и RPC `acquire_deletion_lock`) с использованием `fencing_token`, что защищает от гонок (race conditions). Storage-изображения безопасно удаляются после проверки владения.
- **Корзина (Cart):** Строго ограничивает оформление недоступных (`status != ACTIVE`) или распроданных товаров (проверка `quantity > stock`). Логика обработки и отображения оплаты четко гласит "Рассчитывается отдельно", без фиктивных или небезопасных шлюзов.
- **Чат (Realtime):** Подписки изолированы, создаются с уникальными UUID-маркерами в Strict Mode и корректно уничтожаются через `removeChannel()` при размонтировании.

## 3. Выявленные и устранённые дефекты
Во время Phase 3 были найдены и исправлены следующие реальные дефекты:
- **Next-Intl ключи:** Исправлено некорректное использование длинных текстовых строк внутри функции перевода `t()` на странице `/account-deletion`. 
- **TypeScript типы в Админке:** Скорректированы вызовы `verifyAdminAccess('SYSTEM_CONFIG')` (такого права нет) на существующий `ROLES_MANAGE` для безопасности.
- **Ошибки вывода массивов в Админке:** Исправлено отображение `{full_name}` для связанных сущностей в карточке пользователя (`[id]`).
