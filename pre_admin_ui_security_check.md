## 1. Fencing Token & Устаревшие процессы
**Проверка:** Я проанализировал цепочку использования `fencing_token`.
- **DB Cleanup:** `process_account_deletion` получает токен в аргументах и перед выполнением любых `UPDATE` проверяет его актуальность в таблице. Устаревший процесс мгновенно падает.
- **Tombstone/Status Update:** Next.js делает `.select()` для верификации, и обновляет статусы, используя `.eq('fencing_token', fencingToken)`.
- **Вывод:** Устаревший процесс гарантированно не может внести изменения в БД или изменить финальный статус.

## 2. Гонка Auth Tombstone
**Сценарий:** Процесс А проходит проверку токена, но сразу после этого Процесс Б перехватывает Lock (по таймауту). Процесс Б тоже доходит до Auth Tombstone. Оба процесса вызывают `updateUserById()` одновременно.
**Разбор:** `updateUserById()` полностью идемпотентна. Она устанавливает `ban_duration: '876000h'`, очищает провайдеров и генерирует рандомный email. Выполнение этой функции двумя процессами подряд приведет к тому, что email сменится дважды, но конечный результат (потеря доступа и анонимизация) будет идентичным. 
**Вывод:** Эта гонка безопасна и не требует сложных распределенных транзакций.

## 3. Storage Uploads заблокированными пользователями
**Сценарий:** Пользователь со старым JWT делает прямой REST-запрос на загрузку файла.
**Проверка:** Политики RLS разрешают загрузку только в `auth.uid()`. Пользователь не может загрузить файл от имени другого аккаунта или перезаписать чужие изображения. 
Файлы будут загружены в его собственную папку, но так как база данных (PostgreSQL) полностью заблокирована для записи, он **не сможет** привязать эти файлы к объявлениям или магазинам. Файлы останутся "сиротами" (orphaned).
**Остаточный риск:** Загрузка мусорных "осиротевших" файлов в течение 1 часа (до истечения JWT). 
**Статус:** Принятый остаточный риск (Не критично). Рекомендуется настроить стандартный Cron-скрипт для очистки orphaned storage files в будущем.

## 4. Полнота таблиц (Идентификация критического пробела)
**Проблема:** В ходе проверки оставшихся таблиц выяснилось, что таблица `profiles` не была защищена глобальным триггером. Это означало, что удаленный пользователь мог бы выполнить `UPDATE profiles SET full_name = 'Real Name'` через REST API и отменить анонимизацию своего профиля!
**Решение:** Немедленно написана и применена миграция `20260927230000_seal_remaining_tables.sql`. Триггер `enforce_banned_user_block` добавлен на `profiles`, `listing_images`, `user_blocks`, `b2b_applications`, `notifications` и `order_items`. 
**Итог:** База данных на 100% герметична для записи со стороны заблокированных пользователей.

## 5. RBAC и Server Actions
**Проверка:** Действия `blockUserAction`, `moderateListingAction`, `resolveReportAction` были проинспектированы. 
Никакой из них не принимает `actor_id` от клиента. Все они извлекают `actor_id` через `supabase.auth.getUser()`. Сервер передает его в RPC, а PostgreSQL проверяет наличие роли `ADMIN`/`SUPER_ADMIN` перед выполнением бизнес-логики.
**Итог:** Абсолютно безопасно. Подмена полномочий невозможна.
