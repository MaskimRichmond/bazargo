## 1. Техническая безопасность: RLS и Старые JWT (JWT Expiry Window)

### Анализ уязвимости
Токены Supabase (JWT) являются stateless и валидны до истечения своего TTL (по умолчанию 1 час). 
Функция `supabase.auth.getUser()` делает запрос к бэкенду и мгновенно отклоняет доступ (401), если установлен `ban_duration`. Однако прямые вызовы к защищённым таблицам через REST API (PostgREST) используют локальную валидацию подписи JWT и RLS-политики. Поскольку RLS-политики ради производительности не делают `JOIN profiles`, удалённый пользователь мог бы продолжать создавать объявления в течение 1 часа после удаления аккаунта.

### Принятые меры
- Написана миграция `20260927210000_banned_user_triggers.sql`.
- Добавлен глобальный триггер `enforce_banned_user_block()` на события `INSERT`, `UPDATE`, `DELETE` для критических таблиц (`listings`, `messages`, `orders`, `stores`).
- Триггер проверяет `is_banned` в таблице `profiles` (что является O(1) операцией). Так как при удалении аккаунта мы сразу устанавливаем `is_banned = true`, любая попытка мутации данных мгновенно блокируется базой данных с ошибкой `"Action not allowed for banned or deleted users."`.
- Окно уязвимости для записи данных полностью закрыто (0 секунд). Окно для чтения собственных данных сохраняется до истечения TTL токена (Accepted Residual Risk).

## 2. State Machine и Устойчивость к сбоям

### Анализ архитектуры
Ранее процесс зависел от последовательности вызовов в Next.js без механизмов блокировки одновременных запусков и защиты от зависших состояний (Stuck in Processing).

### Принятые меры
- Создана таблица состояний `public.account_deletion_requests`.
- Разработана RPC `acquire_deletion_lock()`, которая:
  1. Использует пессимистичную блокировку `SELECT ... FOR UPDATE` для защиты от race conditions.
  2. Предотвращает повторный запуск для статуса `COMPLETED`.
  3. Обрабатывает зависшие статусы `PROCESSING` (если `started_at` старше 5 минут, разрешает повторный захват блокировки).
- В `account-deletion.ts` процесс полностью идемпотентен: повторный запуск безопасно проигнорирует уже удаленные из Storage файлы и повторно выполнит DB-очистку без повреждения консистентности.

## 3. Storage и Защита PII

### Анализ и исправления
- Внедрена полная пагинация (по 1000 объектов) при запросах к API Storage (`schema('storage').from('objects').range()`). Это гарантирует, что крупные магазины будут очищены на 100%.
- Удаление происходит пакетами (chunks) по 100 файлов во избежание ограничений на длину URL при HTTP DELETE запросе к Supabase Storage.
- Запись ошибок в State Machine ограничена: чувствительные логи Supabase скрыты. В базу пишется безопасное сообщение `System deletion error occurred` или общие сетевые ошибки, чтобы избежать утечки PII (например, оригинального email) в логи.

## 5. Юридическое заключение (Compliance Disclaimer)

**Юридическая матрица (Кыргызстан):**
- Процесс технически реализует механизм "права на забвение" (Right to Erasure), требуемый стандартами App Store (п. 5.1.1(v)) и местным законодательством (Закон о ПД / Цифровой Кодекс).
- Личные данные (имя, телефон, аватар) заменяются на `Deleted User` (Анонимизация). 
- Связи (Foreign Keys) сохраняются, что не нарушает целостность бухгалтерских/торговых записей (Закон об электронной коммерции КР), но делает пользователя полностью анонимным.

**Важно:** Техническая реализация соответствует лучшим практикам защиты данных, однако этот аудит является инженерным (Technical Security Audit). Он **не заменяет** формальную юридическую экспертизу со стороны Data Protection Officer (DPO) или юристов для сертификации соответствия законодательству КР (Digital Code).
