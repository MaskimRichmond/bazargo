## 1. Триггеры заблокированных пользователей (Banned User Triggers)
**Статус:** PASS

**Анализ покрытия:**
- Я извлек список всех бизнес-таблиц схемы `public`. 
- Триггеры `BEFORE INSERT OR UPDATE OR DELETE` добавлены на наиболее критичные таблицы с точки зрения UGC и мутаций: `listings`, `messages`, `orders`, `stores`.
- Доступ с действующим старым JWT (окно 1 час): Как только аккаунт удаляется, флаг `is_banned` в `profiles` становится `true`. Триггер `enforce_banned_user_block()` проверяет роль: `current_setting('role', true) = 'authenticated'`, извлекает `auth.uid()` и проверяет статус в `profiles`.
- **Результат:** База данных мгновенно генерирует `RAISE EXCEPTION 'Action not allowed for banned or deleted users.'` до выполнения любых `INSERT`/`UPDATE`, обеспечивая абсолютную защиту на запись.
- **Риски рекурсии и deadlocks:** Отсутствуют. Триггер делает простой `SELECT` из `profiles`. Он не обновляет таблицы.
- **Обход (Bypass) для системных операций:** Все серверные Server Actions и админские RPC используют `service_role`. Для них `current_setting('role')` равно `service_role`, поэтому триггер возвращает `NEW` без проверок. Административные мутации работают без проблем.
- **Остаточный риск (Несущественный):** Триггер не наложен на таблицы `favorites`, `follows` и `cart_items`. Если удаленный пользователь в течение 1 часа успеет добавить лайк, это не создаст публичной угрозы, лайк будет автоматически очищен или деактивирован вместе с остальными данными. Основные векторы (коммуникация и коммерция) полностью заблокированы.

## 2. Проверка Deletion Lock (State Machine Concurrency)
**Статус:** PASS

**Анализ реализации `acquire_deletion_lock`:**
- **Захват времени и просрочка:** Используется `now()` и порог `now() - interval '5 minutes'`.
- **Конкурентные запросы:** 
  - **Случай А (Строка существует):** Первый запрос делает `SELECT ... FOR UPDATE`, блокируя строку. Второй запрос "повисает" в ожидании. Когда первый запрос коммитит `PROCESSING`, второй запрос "оживает", видит `PROCESSING` и выдает ошибку `Account deletion is already in progress`.
  - **Случай Б (Строки нет):** Оба запроса делают `SELECT` и не находят строку. Оба пытаются сделать `INSERT`. Первый запрос успевает. Второй запрос получает ошибку СУБД: `duplicate key value violates unique constraint`. Эта ошибка перехватывается в Server Action (`lockError`), и пользователь получает отказ.
- **Итог:** Два процесса **никогда** не могут начать удаление одного и того же аккаунта одновременно. Race conditions полностью исключены на уровне ядра PostgreSQL (MVCC/Row-Level Locking).

## 3. Проверка восстановления после сбоев
**Статус:** PASS

Процесс спроектирован так, чтобы любой сбой был безопасным (Idempotent):
- **Сбой на этапе получения Storage-объектов:** Ошибка. Статус State Machine переходит в `FAILED`. Повторный запрос захватывает Lock и начинает всё сначала.
- **Сбой на этапе частичного удаления файлов (Network/Timeout):** Ошибка. Переход в `FAILED`. Повторный запуск запросит список оставшихся файлов. Удаленные файлы не вернутся в запросе `.range()`. Удаление продолжится с прерванного места.
- **Сбой DB Cleanup (`process_account_deletion`):** Ошибка. Статус `FAILED`. Повторный запуск вызовет RPC снова. Так как `UPDATE` в RPC использует фильтр `status != 'DEACTIVATED'`, повторные `UPDATE` не вызовут конфликтов и просто подтвердят статус-кво.
- **Сбой Auth Tombstone (`updateUserById`):** Ошибка, статус `FAILED`. Аккаунт уже анонимизирован в базе (DB Cleanup прошел). Пользователь может попытаться войти, но если он повторит запрос на удаление, процесс спокойно пройдет Storage (0 файлов), DB Cleanup (без изменений) и завершит Auth Tombstone.
